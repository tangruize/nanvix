Motivation:
Incremental verification for a relatively large and existed codebase.
Minimize changes to executable codes
Improve readability of executable codes for non-verification developers. Do not mix the use of executable code and ghost code.
Avoid extra efforts to install verus toolchain (verus, verusfmt, customized rust-analyzer) for non-verification developer.
Allow project to avoid adding verus (builtin, builtin-macro, and vstd) as a hard dependencies. Projects can easily define their verus_stub procedure macros to control the verus dependency by feature.
Summary
All attribute-base procedure macros only change or insert codes to enable verification when compiling with erase.keep() == true and will not have side effect (verus_spec) or return empty token stream (proof!{}, proof_xxx!{}) when erase.keep() == false

 /*** Verus small macro definition for executable items ***/ 
  
 // If no #[verus_verify] on the item, it is verifier::external by default. 
 // When compiling code with verus: 
 // #[verus_verify] annotates the item with verifier::verify 
 // #[verus_verify(external_body)] annotates the item with verifier::external_body 
 // When compiling code with standard rust tool, the item has no verifier annotation. 
 #[proc_macro_attribute] 
 pub fn verus_verify( 
     args: proc_macro::TokenStream, 
     input: proc_macro::TokenStream, 
 ) -> proc_macro::TokenStream { 
     attr_rewrite::rewrite_verus_attribute(&cfg_erase(), args, input) 
 } 
  
 #[proc_macro_attribute] 
 pub fn verus_spec( 
     attr: proc_macro::TokenStream, 
     input: proc_macro::TokenStream, 
 ) -> proc_macro::TokenStream { 
     attr_rewrite::rewrite_verus_spec(cfg_erase(), attr.into(), input.into()).into() 
 } 
  
 /// proof_with add ghost input/output to the next function call. 
 /// In stable rust, we cannot add attribute-based macro to expr/statement. 
 /// Using proof_with! to tell #[verus_spec] to add ghost input/output. 
 /// Using proof_with outside of #[verus_spec] does not have any side effects. 
 #[proc_macro] 
 pub fn proof_with(_: proc_macro::TokenStream) -> proc_macro::TokenStream { 
     proc_macro::TokenStream::new() 
 } 
  
 /// Add a verus proof block. 
 #[proc_macro] 
 pub fn proof(input: proc_macro::TokenStream) -> proc_macro::TokenStream { 
     attr_rewrite::proof_rewrite(cfg_erase(), input.into()).into() 
 } 
  
 /// proof_decl add extra stmts that are used only 
 /// for verification. 
 /// For example, declare a ghost/tracked variable. 
 /// To avoid confusion, let stmts without ghost/tracked is not supported. 
 /// Non-local stmts inside proof_decl! are treated similar to those in proof! 
 #[proc_macro] 
 pub fn proof_decl(input: proc_macro::TokenStream) -> proc_macro::TokenStream { 
     let erase = cfg_erase(); 
     if erase.keep() { 
         syntax::rewrite_proof_decl(erase, input.into()) 
     } else { 
         proc_macro::TokenStream::new() 
     } 
 } 
  
 /*** End of verus small macro definition for executable items ***/ 

Two attribute procedure macros:
#[verus_spec(...)]: Add specification signature.
#[verus_verify(...)]: Add hints to verifier to mark verifier(external), verifier(external_body), verifier(rlimit(xx)), etc. In additionally, dual_mode is specified via verus_verify.
Three function-like procedure macros:

proof!{...}: proof block similar to proof { ... } inside verus macro
proof_decl!{...}: proof block with function-scoped variables
proof_with!{...}: pass and receive tracked/ghost

Specification signature on loop block
verus_spec will insert other loop specification (e.g, invariant) into the loop block

#[verus_spec(v => ensures true)]
fn test_for_loop(n: u32) -> Vec<u32> {

Proof blocks inside executable function
Inside function body, we prefer to use function-like macro since it does not need to use unstable features.

proof!{} is similar to proof {} inside verus macro, and all variable declared inside proof!{} is scoped to that proof block; This makes verus!{} user see consistant side effect.
proof_decl!{} allows to declare function-scoped variable and in most cases could replace proof!{}.
#[verus_spec]
fn g() {
   proof_decl!{
     let ghost mut i = 0;
     assert(true);
   }
   f();
   proof!{
     assert(i == 0);
   }
}
verus!{
fn g() {
   let ghost mut i = 0;
   proof{
      assert(true);
   }

   f();
   proof{
      assert(i == 0);
   }
}
}

When a function is anotated with verus_spec(with ...), verus_spec procedure macro will generate two version of functions: verus_verified_{xxx} and {xxx} to allow the function to be used by functions inside and outside verification scope.

The unverified function requires false so that not providing correct proof_with!() to pass the tracked/ghost variables to the function will fail the verification.

fn call_unverified(x: u32) {

One limitation is that the current implementation doesn't address how to guard calls to external functions using tracked variables—unless those functions are manually replaced with wrapper functions. This approach, however, causes the executable code to diverge significantly from the original unverified version.

A potential solution to use a procedural macro that recognizes when certain external functions are being guarded by wrapper functions. The mapping between external functions and their verified counterparts could be hard-coded (for standard library functions) or loaded from a configuration file.

For example, a call to core::ptr::read(src: *const T) -> T could be rewritten as vstd::ptr_mut_read(src: *const T, Tracked(perm): Tracked<&mut PointsTo>) -> T in verification mode. The macro would replace core::ptr::read with vstd::ptr_mut_read and insert a corresponding proof_with!(Tracked(perm)) annotation automatically. While this mechanism is theoretically workable, it may be too hacky.

#[verus_spec(
   with Tracked(perm): Tracked(PointsTo<u64>),
  requires ...
)
]
unsafe fn test_ptr_read(src: *const u64) -> u64 {
  proof_with!(Tracked(perm));
  let val = core::ptr::read(src);
  val
}
unsafe fn test_ptr_read(src: *const u64) -> u64 
requires ...
{
  let val = vstd::ptr_mut_read(src, Tracked(perm));
  val
}
I think a better solution is to do such replacement by rust_verifier. It should be more easier to understand and flexible if verifier can identify the extra arguments from assume_specification and the extra arguments from proof_with!().

verus!{
assume_specification [core::ptr::read] (src: *const T,  Tracked(perm): Tracked<&mut PointsTo<T>>) -> (ret: T)
requires ...
ensures ...
}
