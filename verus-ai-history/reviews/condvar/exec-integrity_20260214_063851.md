# Review: condvar Exec Integrity (claude-opus-4.6)

## Grade: A-

## Issues Found

### Critical

- None.

### High

- **Incomplete difference enumeration: `dequeue_first()` not listed.** The
  transformation from `notify_first()` → `dequeue_first()` is not listed as a
  numbered difference in the table, despite involving a return type change
  (`Result<u32, Error>` → `bool`), removal of `ProcessManager::wakeup()`, and
  `unsafe` → safe signature change. The report covers this in the API
  Correspondence table and Exec Logic Fidelity section (#2, "Pop from front"),
  but consistency with difference #13 (`clear()` vs `notify_all()`, which has
  analogous scope changes) requires it to be a numbered entry. The queue
  operation itself (`Vec::remove(0)` ↔ `LinkedList::pop_front()`) is correctly
  identified as semantically equivalent.

### Medium

- **Missing INVENTED_FUNCTION entries for `is_empty()` and `get_len()`.** These
  observer functions do not exist in the original and are new in the verified
  code. They are mentioned in the Verified Properties header ("is_empty and
  get_len are faithful observers of the queue state") but omitted from the
  16-item differences table. While they have no side effects and do not affect
  correctness, the report's own methodology (listing all new functions as
  INVENTED_FUNCTION) should include them. The total count should be 19, not 16.

- **Missing `unsafe impl Send/Sync for CondvarInner` in differences.** The
  original (lines 329–331) has `unsafe impl Send for CondvarInner` and
  `unsafe impl Sync for CondvarInner`. These are not modeled in the verified
  code and not listed in the differences table. Since the report lists
  `impl Debug` (difference #16) as a MISSING_FUNCTION, `Send`/`Sync` impls
  should be listed similarly. These are concurrency-related marker traits,
  consistent with the out-of-scope concurrency model.

### Low

- **`pub` struct fields not listed as a difference.** The original `Condvar`
  has a private `inner: Arc<CondvarInner>` field. The verified model has
  `pub len: usize` and `pub sleeping: Vec<(i32, i32)>`. The code comment
  (line 203) correctly notes "fields are `pub` as required by Verus for
  `pub open spec fn` access," but this visibility change is not captured
  in the differences table as a sub-item of TYPE_CHANGE #1.

- **`spec_kernel_pid()` value not cross-referenced in report body.** The spec
  file defines `spec_kernel_pid() -> int { 0 }`. The report's trust assumption
  T3 area and spec header reference `ProcessIdentifier::KERNEL_RAW` (value 0)
  but the body ("No Logic Divergences Found") does not explicitly confirm the
  cross-reference. Verified: `src/libs/sys/src/sys/pm/pid.rs:51` defines
  `pub const KERNEL_RAW: i32 = 0`, confirming correctness.

## Verification

- **Verification status: PASS** (53 verified, 0 errors). Confirmed
  independently during this review.
- The exec-level queue semantics match the original in all cases:
  - `Vec::push` ↔ `LinkedList::push_back` (FIFO enqueue).
  - `Vec::remove(0)` ↔ `LinkedList::pop_front` (FIFO dequeue).
  - `Vec::remove(idx)` ↔ `LinkedList::remove(at)` (indexed removal).
  - `Vec::clear` ↔ iterative `pop_front` (drain all).
- The `retain()` ↔ `remove_at()` equivalence under uniqueness is correctly
  proven in `lemma_remove_entry_equivalent_to_retain`.
- `debug_assert!` checks in the original `notify_process`/`notify_thread`
  (verifying removed entry matches expected pid/tid) are subsumed by the
  verified model's preconditions, which enforce the match statically — this
  is strictly stronger.
- Trust assumptions T1–T6 are reasonable and well-documented. T4 (sequential
  wait protocol) correctly identifies the fundamental limitation of the
  sequential model vs. runtime concurrency.

## Summary

The integrity report is thorough, well-structured, and correctly identifies all
semantically significant differences between the original and verified exec
code. The core analysis — that all queue state transitions are faithfully
modeled — is sound. The verification passes (53 verified, 0 errors). The
deductions are for incomplete enumeration: `dequeue_first()` should be a
numbered difference (High), and `is_empty()`/`get_len()`/`Send`/`Sync` are
omitted from the table (Medium). These are documentation completeness gaps, not
correctness issues. No semantic divergences were missed that could affect the
verification's validity. The exec code remains faithful to the original
implementation's queue management protocol.
