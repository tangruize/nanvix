# Review: thread_state Exec Integrity (claude-opus-4.6)

## Grade: A

## Issues Found

### Critical

- None.

### High

- **`store_mutex_guard` parameter reduction not explicitly documented.** The original takes two parameters (`address: MutexAddress, guard: MutexGuard`); the verified version takes one (`address: u64`). The `guard` parameter is dropped entirely because `MutexGuard` is an opaque RAII token. This is covered implicitly by TYPE_CHANGE #5 ("MutexGuard payload is opaque") but should be an explicit line item since it changes the function's arity, not just its types.

- **`take_mutex_guard` return type change not an explicit line item.** The original returns `Option<MutexGuard>`; the verified version returns `()`. The report discusses this in T2's justification and the equivalence table, but the difference table (#15) only mentions ghost annotations. A function's return type changing from `Option<MutexGuard>` to `()` is a structural change that merits its own TYPE_CHANGE or SIGNATURE_CHANGE entry.

### Medium

- **Function visibility change not documented.** All 12 `pub(super)` functions in the original become `pub` in the verified code. The report documents field visibility changes (#7) but not function visibility. While this is necessary for Verus (same reason as fields), it should be noted for completeness — the justification is identical to #7 and could be folded into it.

- **Parameter type changes in function signatures only implicitly covered.** The following parameter/return type changes are consequences of the documented field TYPE_CHANGEs but are not individually enumerated: `MutexAddress` → `u64` (in `store_mutex_guard`, `take_mutex_guard`), `InterruptReason` → `int` (in `set_interrupt_reason`), `Option<InterruptReason>` → `Option<int>` (return of `take_interrupt_reason`), `Option<KernelStack>` → `Option<int>` (return of `take_kernel_stack`), `Option<UserStack>` → `Option<int>` (return of `take_user_stack`), `Option<VirtualAddress>` → `Option<int>` (in `store_thread_data_area`, return of `get_thread_data_area`). These follow directly from #1–#5 and are arguably implied, but explicit enumeration would strengthen the report.

### Low

- **`new()` parameter list change (6 → 4 params) noted only in doc comment.** The omission of `context: ContextInformation` and `fpu_state: FpuState` parameters is documented in the verified code's doc comment ("Omitted Parameters") and covered by #6, but the difference table doesn't have a dedicated entry for the constructor signature change.

## Detailed Analysis

### 1. Were ALL differences identified?

**Mostly yes.** The 20 enumerated differences cover the field-level type abstractions, ghost annotations, function omissions, and the invented `check_drop_safe`. However, several function-signature-level differences (parameter counts, parameter types, return types, visibility) are only implicitly covered by the field-level TYPE_CHANGE entries rather than being explicitly listed. These are all *consequences* of the documented abstractions, so nothing semantic is missed, but the report would be stronger with explicit signature-level entries.

### 2. Were LOGIC_CHANGE items correctly handled?

**N/A — no LOGIC_CHANGE items were found.** This is correct. Independent diff confirms all exec bodies faithfully implement the original logic within the abstraction boundaries.

### 3. Are there remaining semantic differences that were missed?

**No meaningful semantic differences were missed.** The `store_mutex_guard` parameter reduction and `take_mutex_guard` return type change are the closest to semantic differences, but both are well-justified under the protocol-only modeling approach (guard payload is opaque, T1/T2 formalize kernel invariants). The `BTreeMap::insert` return value (old value on duplicate key) is safely ignored because T1 prevents duplicate keys and the original code discards the return value.

### 4. Is the exec code faithful to the original?

**Yes.** Within the documented abstraction boundaries:
- All `Option::take()` calls are correctly modeled as manual `let v = self.field; self.field = None; v` (required because Verus doesn't support `.take()` directly).
- `BTreeMap::insert` is faithfully modeled by `Vec::push` + counter increment under T1 (no duplicates).
- `BTreeMap::remove` is faithfully modeled by linear scan + `Vec::remove` + counter decrement under T2 (address always found).
- Simple field assignments (`set_interrupt_reason`, `store_thread_data_area`) are identical.
- Simple field reads (`id`, `get_thread_data_area`) are identical.

### 5. Does verification still pass?

**Yes.** 47 verified, 0 errors — confirmed independently.

## Summary

The integrity report is thorough, well-structured, and correctly identifies all semantically meaningful differences between the original and verified exec code. The type abstractions are well-justified (opaque HAL types, Pin/Box/BTreeMap), the trust assumptions (T1: no double-lock, T2: release-what-you-hold) are sound formalizations of real kernel invariants, and the invented `check_drop_safe()` is properly proven equivalent to the original `Drop` check. The grade is A rather than A+ due to several function-signature-level differences (parameter count/type changes, return type changes, visibility changes) that are implicitly covered by field-level entries but would benefit from explicit enumeration for a fully self-contained audit trail. No logic changes were found or missed.
