# Review: running_thread Exec Integrity (claude-opus-4.6)

## Grade: A-

## Issues Found

### Critical

- None.

### High

- **Mutex address type width mismatch not documented.** The original `MutexAddress` wraps `VirtualAddress(usize)`, which is 32-bit on the x86 target. The verified code uses `u64` for `store_mutex_guard` / `take_mutex_guard`. The report (item 12, 13) says "MutexAddress is a newtype over an integer" but does not call out the 32→64 bit widening. Since the spec reasons about `address as int` and verifies protocol-level properties (membership, counting) rather than address arithmetic, this is semantically harmless but should be documented as a type abstraction detail. Risk: Low.

### Medium

- **`#[derive(Debug)]` removal not listed.** The original `RunningThread` has `#[derive(Debug)]`; the verified struct does not. This is cosmetic (no exec logic impact), but the report claims 13 total differences and this makes it 14. It should appear as a trivial `TRAIT_REMOVAL` or `ACCEPTABLE` entry for completeness.

- **`mut self` → `self` parameter change not called out.** Functions `sleep()`, `schedule()`, and `exit()` use `mut self` in the original (needed for `self.state.context_mut()`) but plain `self` in the verified code. This is a direct consequence of omitting the `context_mut()` call and is semantically irrelevant (the value is consumed either way), but it is a syntactic difference that could be noted under the existing TYPE_CHANGE items for completeness.

### Low

- **Report header comment inconsistency.** The module-level doc comment in `running.rs` says "MutexAddress -> Ghost<int> (abstract address)" but the actual exec parameter type is `u64`, not `Ghost<int>`. The `Ghost<int>` interpretation applies at the spec level only. The doc should say "MutexAddress -> u64 (exec) / int (spec)".

## Detailed Verification

### 1. Were ALL differences identified?

Nearly all. The report correctly identifies 13 differences covering struct layout, type abstractions, ghost annotations, and function omissions. Three minor items are missing:
1. `#[derive(Debug)]` removal (cosmetic).
2. `mut self` → `self` on three functions (consequence of `context_mut()` removal).
3. Address type width change `usize` (32-bit) → `u64` (64-bit).

None of these affect exec logic correctness.

### 2. Were LOGIC_CHANGE items correctly handled?

No items were categorized as LOGIC_CHANGE. This is correct — there are no actual logic changes. The two API-strengthening preconditions (T1: no double-lock on `put_mutex_guard`, T2: release-only-held on `take_mutex_guard`) are properly documented in the Trust Boundary section rather than as LOGIC_CHANGE, which is appropriate since they are ghost-level preconditions that do not alter exec control flow.

### 3. Are there remaining semantic differences?

No material semantic differences were missed. The exec code faithfully delegates to the same `ThreadState` methods with equivalent arguments (modulo type abstraction). The `*mut ContextInformation` omission is properly justified as a HAL boundary concern.

One subtlety worth noting: the original `sleep()` calls `self.state.context_mut()` *before* moving `self.state` into `SleepingThread::from_state()`. This means the raw pointer is obtained from the state that then gets moved into the `SleepingThread`. The verified model correctly omits this unsafe aliasing pattern, and the report rightly classifies it as a HAL boundary omission.

### 4. Is the exec code faithful to the original?

Yes. The Exec Logic Correspondence table in the report is accurate. Every exec function body in the verified code performs the same delegation as the original:
- `from_state`: wraps state in struct. ✅
- `sleep`: delegates to `SleepingThread::from_state(self.state, alarm)`. ✅
- `schedule`: delegates to `ReadyThread::from_state(self.state)`. ✅
- `id`: returns `self.state.id()`. ✅
- `thread_state`: returns `&self.state`. ✅
- `thread_state_mut`: returns `&mut self.state` (external). ✅
- `exit`: delegates to `ZombieThread::from_state(self.state, status)`. ✅
- `put_mutex_guard`: delegates to `self.state.store_mutex_guard(address)`. ✅
- `take_mutex_guard`: delegates to `self.state.take_mutex_guard(address)`. ✅

The boundary models for `SleepingThread`, `ReadyThread`, and `ZombieThread` are clean verification scaffolding with explicit cross-module obligations documented.

### 5. Does verification still pass?

Yes. Verified: 47, Errors: 0. Confirmed independently during this review.

## Summary

The integrity report is thorough and well-organized. All 9 exec functions are accounted for, with the `join_cond()` omission properly justified. The type abstractions (`Box` removal, `SystemTime`→`int`, `ExitStatus`→`int`, `MutexAddress`→`u64`, `MutexGuard` elision, `*mut ContextInformation` omission) are all well-justified with clear documentation of trust boundaries and verification model decisions. The API-strengthening preconditions (T1, T2) are correctly identified and documented with appropriate risk assessment.

The grade of A- reflects three minor documentation gaps: (1) the `#[derive(Debug)]` removal is not listed, (2) the `usize`→`u64` type widening is not called out, and (3) the `mut self`→`self` parameter change is not explicitly noted. None of these affect correctness or verification soundness — they are completeness issues in the report's difference enumeration.
