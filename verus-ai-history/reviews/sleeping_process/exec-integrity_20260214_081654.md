### Medium

1. **Unlisted visibility change on `new()`**: Original declares `pub(super) fn new(...)`, verified code declares `pub fn new(...)`. This widens accessibility from module-sibling-only to fully public. Not mentioned in the difference table. Impact: low — the verification model doesn't enforce access control and this is an artifact of Verus module boundaries — but it should have been documented as a TYPE_CHANGE or noted in the analysis since the original deliberately restricts the constructor.

2. **Unlisted `trace!` elision in `add_thread()`**: Original line 179 has `trace!("self.pid={:?}, ready_thread={:?}", self.state.pid, ready_thread);`. The verified code omits this entirely. The report does not mention this difference. Impact: none for verification (logging is a side-effect), but the difference table claims "Total differences: 14" while there are at least 16 actual differences. Should be listed as GHOST_ANNOTATION/acceptable (logging elision).

3. **`ThreadIdentifier` → `u64` parameter type changes not explicitly listed**: Parameters `tid: ThreadIdentifier` in `wakeup()`, `find_thread()`, `find_thread_mut()` are all changed to `tid: u64`. While this is implied by the overall type abstraction model, it is not called out as a separate difference the way the oracle parameters (#4, #5) are. It would be clearer to document this once as a blanket TYPE_CHANGE.

### Low

4. **`mut self` → `self` in `wakeup()` and `add_thread()`**: The original uses `mut self` for `wakeup()` and `add_thread()` (needed for `.take()` and reassignment in error paths). The verified code uses `self` (non-mut) because the verified control flow avoids in-place mutation. This is semantically correct but not documented.

5. **`now: SystemTime` parameter removed in `wakeup_alarm()`**: Difference #5 notes the oracle replacement but does not explicitly document the removal of the `now: SystemTime` parameter, which is a concrete interface change. The oracle parameters (`has_expired`, `interrupted_ids`, `remaining_ids`) replace it, but the removal itself should be listed.

### 3. Are there remaining semantic differences?

**No significant semantic differences were missed.** The key semantic concern is `wakeup_alarm()`'s oracle approach, which pushes per-thread alarm comparison logic to a trust boundary. The report correctly identifies this (difference #5, Trust Boundary #3). The oracle preconditions are comprehensive:
- Length conservation: `interrupted_ids@.len() + remaining_ids@.len() == self.sleeping_thread_ids@.len()`
- Content conservation: all partition elements come from the original sleeping list.
- No duplicates within partitions.
- Disjointness between partitions.
- Subsequence ordering (stable partition semantics).
- Identity preservation when no alarm expired: `!has_expired ==> remaining_ids@ =~= self.sleeping_thread_ids@`.

These constraints are sufficient to verify all structural properties of the partition without modeling alarm data.
