## Detailed Analysis

### 1. Were ALL differences identified?

**Mostly yes, with three omissions.** The report identifies 12 differences covering all major type modeling, ghost fields, ghost annotations, and external_body decisions. Three differences were missed:
1. `tid` parameter type change (`ThreadIdentifier` → `u64`) in `find_thread`/`find_thread_mut`.
2. `#[derive(Debug)]` removal from the struct.
3. `new()` visibility change (mentioned but not numbered).

None of these omissions are logic changes; they are all consistent with the design-level modeling approach.

### 2. Were LOGIC_CHANGE items correctly handled?

**N/A — no LOGIC_CHANGE items were identified.** All 12 differences were classified as TYPE_CHANGE, GHOST_FIELD, or GHOST_ANNOTATION. This classification is substantively correct: the verified code preserves all control flow, data flow, and decomposition logic of the original. The constructor assigns fields directly (same pattern), `bury()` returns fields in the same tuple order, and search functions are modeled via spec contracts.

### 3. Are there remaining semantic differences?

**No material semantic differences remain.** The exec code is a faithful model of the original under the declared type abstractions:
- `NonEmptyVecDeque<ZombieThread>` → `Vec<u64>` with `len() >= 1` invariant.
- `Box<ProcessState>` → `u64` (PID only).
- `ExitStatus` → `i64`.
- `ThreadIdentifier` → `u64`.

The `zombie_count` ghost field is redundant with `zombie_thread_ids.len()` but serves as exec-level bookkeeping to bridge ghost/exec reasoning. The `wf()` invariant correctly ties them together.

### 4. Is the exec code faithful to the original?

**Yes.** Specific verification points:
- **Constructor**: Same assignment pattern — each field is directly initialized from a parameter. Parameter order differs (pid first vs process first) but this is inconsequential.
- **`state()`**: Original returns `&self.process`, verified models as PID extraction. Correct abstraction for identity-focused reasoning.
- **`state_mut()`**: Original returns `&mut self.process`, verified returns PID with frame conditions. PID immutability is verified cross-module in `process_state` — all 15 listed public mutators have verified `self.spec_pid() == old(self).spec_pid()` postconditions. The `pid` field is private with no setter.
- **`bury()`**: Tuple order preserved: (zombie_threads, process/pid, status). Field names differ but semantics match.
- **`find_thread()`/`find_thread_mut()`**: External_body with spec contracts. `spec_find_thread` correctly models the search: `Some(0)` when thread exists, `None` otherwise. The `0u64` tag represents "found in zombie list" (ZombieProcess only has one thread list, so the tag is unambiguous). Frame conditions on `find_thread_mut` correctly assert that the function itself doesn't modify any ZombieProcess fields.

### 5. Does verification pass?

**Yes.** Verification passes with 25 verified, 0 errors — consistent with the report's claimed status. No regressions.
