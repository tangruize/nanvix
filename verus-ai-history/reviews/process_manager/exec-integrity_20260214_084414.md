## Issues Found

### Critical

- None.

### High

- None.

### Medium

1. **Scheduling order equivalence not explicitly argued.** The original `schedule()` (mod.rs:640-678) performs: (1) push running→ready, (2) `check_alarm()`, (3) resume all interrupted→ready, (4) `take_earliest_ready`. The verified `full_schedule` composes `resume_all_interrupted` + `schedule` (which itself does push running + pop chosen_next). The `alarm_interrupt` calls are expected externally *before* `full_schedule`. This means the running process is still "running" during alarm checks in the verified model, whereas in the original it is already in the ready queue. The report does not explicitly argue that this reordering is semantically equivalent. **Assessment:** It IS equivalent because `check_alarm` only operates on `suspended→interrupted` and never inspects or modifies the ready queue, so the running process's queue membership during alarm processing is irrelevant. The report's compositional model in the spec file (lines 179-188) describes the decomposition but omits this equivalence argument. This is a documentation gap, not a correctness issue.

### Low

1. **`try_wakeup` ready-queue wakeup path under-documented.** The original `try_wakeup` (mod.rs:847-872) searches the ready queue, removes a process, calls `wakeup(tid)`, and either returns `Some(runnable)` (success → caller pushes back to ready) or pushes back and returns `None` (failure). Both cases are net no-ops at the queue level. The report's item #9 covers this via `wakeup_ready_noop` but does not trace the remove-then-reinsert sequence for the ready-queue path. This is acceptable since the net effect is correctly modeled.

2. **`harvest_zombies` pops one zombie per call, not all.** The original (mod.rs:1191-1208) pops exactly one zombie via `self.zombies.pop_front()`, returns `Some(...)` or `None`. The outer `ProcessManager::harvest_zombies` (mod.rs:1737-1782) calls this once. The verified `harvest_zombie` models removing one zombie, and `harvest_zombies_wrapper` documents the inductive argument. The report correctly covers this (item #16), but the wording "Modeled as `harvest_zombie(&mut self, pid)` (single zombie)" could be more explicit that the original also processes one zombie per call.
