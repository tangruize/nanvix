### 2. Were LOGIC_CHANGE items correctly handled?

**Yes.** The report correctly identifies zero LOGIC_CHANGE items requiring fixes. I verified:

- **get_mutex:** Original `entry().or_insert_with().clone()` is faithfully modeled as
  "if present, increment ref count; else insert with ref_count=2." Initial ref_count=2 correctly
  models `Arc` semantics (1 in map + 1 returned clone). The capacity check
  `self.mutex_count >= MUTEX_MAX_EXEC()` matches `self.mutexes.len() >= MUTEX_OPEN_MAX`. The known
  over-conservative capacity bug (rejecting existing keys at capacity) is documented and faithfully
  replicated.

- **put_mutex:** Original `extract_if` with `|&addr, mutex| mutex_addr == addr && mutex.reference_count() <= 2`
  is equivalent to the verified conditional removal at `idx` when `ref_count_at_threshold`. BTreeMap
  uniqueness ensures at most one entry matches. The non-threshold path (ref_count > 2) correctly
  does nothing in both versions.

- **get_cond / put_cond:** Same patterns as mutex, with `COND_REMOVE_THRESHOLD = 1` matching
  original's `reference_count() <= 1`. Initial ref_count=2 is correct (same Arc clone semantics).

- **remove_pmio:** Original `iter().position().remove()` faithfully modeled with externalized
  `found`/`found_idx` parameters. First-occurrence precondition enforced. Return type change
  (`AnyIoPort` → `()`) is justified since `AnyIoPort` is opaque.

### 3. Remaining semantic differences missed?

**No material differences missed.** I examined:

- **Overflow safety:** `mutex_count + 1` is safe (capacity < 32 < usize::MAX). Ref count increment
  has precondition `< u64::MAX`. `mutex_count - 1` is safe (entry existence + wf ensures count > 0).
  All arithmetic is correctly bounded.

- **`extract_if` laziness:** The original's `extract_if().collect()` is correctly modeled as direct
  conditional removal. The `.collect()` is what triggers removal in the original; without it, nothing
  happens.

- **Threshold asymmetry:** `MUTEX_REMOVE_THRESHOLD = 2` vs `COND_REMOVE_THRESHOLD = 1` faithfully
  matches the original's `reference_count() <= 2` vs `reference_count() <= 1`. This is a real design
  asymmetry in the original code, correctly preserved.

- **External body stubs:** All 10 stubs have appropriate frame conditions (preserving pid,
  capabilities, mutexes, condvars, pmio, wf). Read-only stubs (`vmem_stub`, `read_pmio_stub`,
  `copy_*_stub`, `get_pmio_stub`, `debug_fmt_stub`) use `ensures true`, which is correct.

### 4. Is the exec code faithful?
