# Review: semaphore Exec Integrity (claude-opus-4.6)

## Grade: A-

## Issues Found

### Critical

- None.

### High

- **Missed difference: `unsafe` keyword removal.** The original `down(&self)` and
  `up(&self)` are `unsafe fn`. The verified `down_available`, `down_or_block`, and
  `up` are safe `fn` (with ghost `CallerContext` parameters encoding the safety
  obligations). The removal of `unsafe` is not listed as an explicit difference in
  the report table (items 1–16). It is *referenced* in trust assumption T4 and in
  the doc comments for items 11, 12, and 14 (GHOST_ANNOTATION), but never catalogued
  as its own TYPE_CHANGE or API_CHANGE entry. This is a user-visible API signature
  change that should have a dedicated row. Impact: low (the safety encoding via
  `CallerContext` is correct and well-documented), but completeness of the diff
  inventory is reduced.

### Medium

- **Difference 1 conflates type change and visibility change.** The report lists
  `value: AtomicUsize` → `pub value: usize` as a single TYPE_CHANGE. This is
  actually two independent changes: (a) `AtomicUsize` → `usize` (type), and
  (b) private → `pub` (visibility). The visibility change violates the Nanvix
  coding standard ("Member fields in structs must be private and accessed via
  getter/setter methods") and is only justified by a Verus tooling constraint.
  While the code documents this exception, the report should separate the two
  changes to make the coding-standard deviation explicit and auditable.

- **`DownOutcome` enum not listed as an invented type.** The report lists two
  INVENTED_FUNCTIONs (`get_value`, `is_available`) but does not list the
  `DownOutcome` enum (defined in `semaphore.spec.rs`, used as exec return type
  of `down_or_block`). While `DownOutcome` is referenced in difference 7, it
  should be catalogued as an INVENTED_TYPE for completeness, since it is a new
  type visible in the exec API that has no counterpart in the original.

### Low

- **Import changes not listed.** The original imports `Condvar`, `AtomicUsize`,
  `Ordering`, `Error`, `ErrorCode`, and `SleepError`. The verified code imports
  `vstd::prelude::*` and includes spec/proof files via `include!()`. These are
  consequential changes driven by the other differences, but for a complete diff
  inventory they should be noted (even if just as a blanket "import changes
  follow from the sequential model" entry).

## Detailed Verification

### 1. Were ALL differences identified?

**Mostly yes, with gaps noted above.** The 16 catalogued differences cover the
substantive changes comprehensively. The three gaps (unsafe removal, visibility
change separation, DownOutcome type) are omissions of categorization rather than
missed semantic changes — the report *references* all of them in prose or related
entries, but does not give them dedicated diff-table rows.

### 2. Were LOGIC_CHANGE items correctly fixed or properly justified?

**Yes.** All three LOGIC_CHANGE items (7, 8, 9) are properly justified:

- **Item 7 (down split):** The `down()` → `down_available()`/`down_or_block()`
  split is well-justified. The core arithmetic `if value > 0 { value -= 1 }` is
  preserved identically. The `fetch_update(|v| if v==0 {None} else {Some(v-1)})`
  closure is semantically equivalent for `usize` (where `v != 0` ⟺ `v > 0`).
  Verified by inspecting the exec code at lines 304–309 of `semaphore.rs`.

- **Item 8 (loop removal):** The `loop { ... Condvar::wait(None)? }` removal is
  correctly justified. The blocking path is modeled at spec level via
  `spec_down_blocking()` and `spec_wake()`, with proof lemmas
  (`lemma_down_blocking_preserves_wf`, `lemma_wake_preserves_wf`,
  `lemma_all_waiters_eventually_served`) verifying the abstract protocol.
  The limitation (liveness/progress not modeled) is explicitly scoped out.

- **Item 9 (notify removal):** The `sleeping.notify_first().map(|_awakened| ())`
  removal is correctly justified under T5. The wake effect is modeled by
  `spec_wake()` and proved consistent via `lemma_condvar_interface_consistent`.

### 3. Are there remaining semantic differences that were missed?

**No material semantic differences were missed.** The three categorization gaps
noted above (unsafe removal, visibility change, DownOutcome type) do not represent
missed *semantic* changes — they are organizational omissions in the diff table.
The core semaphore protocol (decrement-if-positive, increment, blocking/waking)
is faithfully preserved.

One subtle point worth noting: the original `up()` returns `Result<(), Error>` —
if `notify_first()` fails, the error propagates and the caller knows the wake
failed (value was still incremented). In the verified model, `up()` always
succeeds (returns `()`). This means the **error-on-wake** path is lost. The
report correctly documents this as T5, but it's worth emphasizing that callers
of the original `up()` that handle the error case have no verified counterpart.

### 4. Is the exec code still faithful to the original implementation?

**Yes.** The core exec logic equivalence table in the report is accurate:

| Original | Verified | Equivalent? |
|----------|----------|-------------|
| `AtomicUsize::new(value)` | `Semaphore { value }` | ✓ Same initial value |
| `fetch_update(\|v\| if v==0 {None} else {Some(v-1)})` | `if self.value > 0 { self.value -= 1 }` | ✓ Identical decision + decrement |
| `fetch_add(1, SeqCst)` | `self.value = self.value + 1` | ✓ Same increment |

Additionally confirmed:
- `try_down()` correctly preserves both success and failure paths.
- `up()` overflow guard (`value < usize::MAX`) makes explicit what `fetch_add`
  silently wraps — this is strictly *more conservative* than the original.
- The `down_or_block()` WouldBlock path correctly leaves exec state unchanged
  (only ghost waiter count incremented via spec-level transition).
- `get_value()` and `is_available()` are pure accessors with no side effects.

### 5. Does verification still pass?

**Yes.** Verification passes: 44 verified, 0 errors (confirmed by running
`./verus-ai/scripts/verify.sh semaphore`).

## Summary

The integrity report is thorough and well-structured. It correctly identifies all
substantive semantic differences between the original and verified exec code,
provides accurate core logic equivalence mappings, and documents trust assumptions
comprehensively. The verified exec code faithfully preserves the semaphore protocol
arithmetic while replacing concurrent primitives with a sequential model amenable
to Verus verification. The three categorization gaps (unsafe removal not catalogued
as a separate diff entry, visibility change conflated with type change, DownOutcome
not listed as an invented type) are organizational rather than substantive — all
underlying changes are referenced in the report's prose. The module documentation
