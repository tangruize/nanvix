### 1. `allocate` - Error Case Strengthening

**Location:** Line 1846

**Before:**
```rust

```

**After:**

**Rationale:** The original spec only said the state is unchanged on error, but didn't explain *why* the error occurred. The strengthened spec makes explicit that errors only happen when the slab has no free capacity (`!can_allocate()`). This is the dual of the existing liveness property `can_allocate() ==> result is Ok`.

### 4. `deallocate` - Enables Future Allocation

**Location:** Lines 2039-2041

**Before:**
```rust
&&& forall|i: int| 0 <= i < self@.num_data_blocks && i != block_idx ==>
    self@.is_allocated(i) == old(self)@.is_allocated(i)
// (no liveness property about allocation)
```

**After:**
```rust
&&& forall|i: int| 0 <= i < self@.num_data_blocks && i != block_idx ==>
    self@.is_allocated(i) == old(self)@.is_allocated(i)
// Liveness: after deallocation, allocation is possible (at least one free block).
&&& self@.can_allocate()
```

**Rationale:** After deallocating a block, that block becomes free, guaranteeing that `can_allocate()` is true. This is a crucial liveness property: freed resources become available for reuse. The proof uses set cardinality reasoning: the deallocated block is in the valid range but not in `allocated_blocks`, so `used < capacity`, thus `free > 0`.

## Proof Additions

The `can_allocate()` postcondition for `deallocate` required substantial proof work:

1. Establish that the deallocated block index is in valid range
2. Show the block is no longer in `allocated_blocks` after clearing
3. Prove `allocated_blocks` is a strict subset of `[0, num_data_blocks)` using set insertion lemma
4. Conclude `|allocated_blocks| < num_data_blocks`, thus `used < capacity` and `can_allocate()`

The proof uses `axiom_set_insert_len` to show that inserting the witness (deallocated block) into `allocated_blocks` increases cardinality by 1, and since this augmented set is still a subset of the full range, the original set must be strictly smaller.
