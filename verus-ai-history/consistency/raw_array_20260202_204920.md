## Semantic Analysis

### RawArrayStorage Functions
All four original functions (`new_managed`, `new_unmanaged`, `get`, `get_mut`) are implemented identically in the Verus version. The functions are placed outside the `verus!` block and are not verified directly, but serve as the foundation for the verified `RawArray` type.

### RawArray Constructor Functions
- `new()`: Semantically equivalent. Requires `len > 0` and `len < i32::MAX`, matching original bounds check.
- `from_raw_parts()`: Semantically equivalent. Preserves all safety requirements from original.

### Access Functions
The original uses `Deref` and `DerefMut` traits for slice access:
- `deref()` returns `&[T]` - **Implemented** in Verus version
- `deref_mut()` returns `&mut [T]` - **Cannot be implemented** in Verus (doesn't support `&mut` return in trait impls)

To compensate for missing `DerefMut`, the Verus version adds:
- `set(index, value)` - provides mutable access with full verification of bounds, length preservation, and frame condition
- `get(index)` - provides immutable access alternative
- `len()` - provides direct length access

These invented functions are justified because:
1. They provide verified access patterns that cannot be achieved via `DerefMut`
2. They preserve the semantic intent of the original (mutable array access)
3. They add strong verification guarantees (bounds checking, frame conditions)

### Drop Implementation
The original `Drop` deallocates memory for `Managed` storage using the allocator. The Verus version now matches this exactly:
- For `Managed` storage: Computes layout and calls `dealloc`
- For `Unmanaged` storage: No-op (as in original)

The implementation uses `#[verifier::external]` because Verus doesn't support `opens_invariants` on Drop traits.

## Remaining Concerns
1. **Invented Functions**: The invented functions (`from_raw_addr`, `set`, `get`, `len`, `storage_len`) are not in the original source. While justified for verification purposes, they change the public API. Code using the original `RawArray` via `DerefMut` would need to be adapted to use `set()` method instead.

2. **View Abstraction**: The Verus version uses an `uninterp spec fn view()` for the abstract view. This is sound for verification but means the actual memory contents are trusted rather than verified.

3. **Zero Initialization Axioms**: The zero-initialization specification uses axioms (`axiom_u8_zero_is_0`, etc.) which are trusted assumptions. This is appropriate since Verus cannot verify the behavior of `ptr::write_bytes`.
