## Summary
- Total differences: 14

## Overview

The verified mutex is a **sequential state-machine model**, not a direct transliteration
of the original concurrent implementation. The original uses `AtomicBool` interior
mutability, `Arc` shared ownership, `Condvar` thread sleeping, and RAII `MutexGuard`
with `Drop`. None of these are expressible in Verus, so the verified model uses plain
`bool` fields, `&mut self` exclusive references, and explicit `MutexToken` ghost tokens.

The module header documentation extensively describes the verification model, API mapping,
trust boundaries, trust assumptions, and a refinement argument connecting the sequential
model to the concurrent implementation.

All executable logic in the verified code faithfully models the corresponding logic in the
original, within the scope of the sequential model.

## Exec Logic Comparison

### `try_lock()` — Faithful ✓

| Aspect | Original | Verified |
|--------|----------|----------|
| Guard check | `compare_exchange(false, true, Acquire, Relaxed).is_err()` | `if !self.locked` |
| Lock action | Implicit in successful CAS | `self.locked = true` |
| Success return | `Ok(MutexGuard { mutex: self.0.clone() })` | `(true, Tracked(Some(token)))` |
| Failure return | `Err(())` | `(false, Tracked(None))` |

The sequential `if !self.locked { self.locked = true }` is the linearization-point
equivalent of `compare_exchange(false, true)` (see Refinement Argument in module header).

### `lock()` — Structurally divergent, documented ⚠

| Aspect | Original | Verified |
|--------|----------|----------|
| Loop | `loop { ... }` | Single call |
| Blocking | `condvar.wait(timeout)?` | None (precondition guarantees success) |
| Timeout | `Option<SystemTime>` parameter | Not modeled |
| Error | `SleepError` on timeout/interrupt | None |

The original `lock()` is a **blocking** operation that may sleep. The verified model's
`spec_is_unlocked()` precondition eliminates contention, so the loop body executes
exactly once. This is the documented limitation of the sequential model.

### `unlock()` (modeling `unlock_unchecked` + `Drop`) — Faithful ✓

| Aspect | Original | Verified |
|--------|----------|----------|
| Unlock action | `self.locked.store(false, Relaxed)` | `self.locked = false` |
| Condvar notify | `self.sleeping.notify_first()` | Not modeled (external dep) |
| Error handling | `warn!()` on notify failure | Not modeled |
| Token cleanup | N/A | `self.token_issued = false` |

### `new()` — Faithful ✓

| Aspect | Original | Verified |
|--------|----------|----------|
| Initial state | `AtomicBool::new(false)` | `locked: false` |
| Condvar | `Condvar::new()` | Not modeled |
| Wrapping | `Arc::new(MutexInner { ... })` | Flat struct |
| Identity | Implicit (Arc pointer) | Explicit `id` parameter |

## Conclusion

The verified mutex code is a faithful **sequential state-machine model** of the original
concurrent implementation. All exec-level logic (lock/unlock state transitions) correctly
mirrors the original. The structural divergences (plain `bool` vs `AtomicBool`, `&mut self`
vs `&self`, explicit tokens vs RAII guards, no loop/condvar in `lock()`) are necessitated
by Verus's modeling constraints and are extensively documented in the module header with
trust boundaries, trust assumptions, and an informal refinement argument.

No fixes were required. All differences are either ghost annotations, ghost fields for
verification tracking, or documented structural adaptations for sequential verification.
