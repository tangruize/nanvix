## Overview

The verified exec code is a **sequential specification model**, not a drop-in replacement
for the original. The module header extensively documents this design decision (see
"Verification Model", "API Mapping", "API Divergence", "Trust Assumptions" sections).
All exec logic that maps to the original is semantically equivalent: the core arithmetic
of `try_down`, `down`, `up`, and `new` is preserved. Differences arise from modeling
`AtomicUsize` as plain `usize`, removing `Condvar` (modeled at spec level), and simplifying
`Result` return types.

## Trust Assumptions (from module documentation)

- **T1**: No arithmetic overflow — `up()` precondition `value < usize::MAX` makes explicit what `fetch_add` silently wraps.
- **T2**: Condvar correctness — sleep/wake protocol modeled at spec level only.
- **T3**: Sequential ordering — model assumes sequential execution; original uses `SeqCst`.
- **T4**: Caller safety conditions — encoded as `Ghost<CallerContext>` preconditions.
- **T5**: `notify_first()` success — original returns `Result`, model assumes success.
- **T6**: `Condvar::wait()` success — original returns `Result<(), SleepError>`, model preconditions guarantee success path.

## Conclusion

All 16 differences are documented and justified. The verified exec code preserves the
core semaphore arithmetic (decrement-if-positive for down/try_down, increment for up)
while replacing concurrent primitives (`AtomicUsize`, `Condvar`) with a sequential model
amenable to Verus verification. The two invented functions are side-effect-free accessors
used only for proof connectivity. No fixes required.
