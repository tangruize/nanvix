## Overview

The verified exec code is a **sequential specification model**, not a drop-in replacement
for the original. The module header extensively documents this design decision (see
"Verification Model", "API Mapping", "API Divergence", "Trust Assumptions" sections).
All exec logic that maps to the original is semantically equivalent: the core arithmetic
of `try_down`, `down`, `up`, and `new` is preserved. Differences arise from modeling
`AtomicUsize` as plain `usize`, removing `Condvar` (modeled at spec level), and simplifying
`Result` return types.

## Core Exec Logic Equivalence

| Original | Verified | Equivalent? |
|----------|----------|-------------|
| `AtomicUsize::new(value)` | `Semaphore { value }` | ✓ Same initial value |
| `fetch_update(\|v\| if v==0 {None} else {Some(v-1)}).is_ok()` (down) | `if self.value > 0 { self.value -= 1; Acquired } else { WouldBlock }` | ✓ Same decision + decrement |
| `fetch_update(\|v\| if v==0 {None} else {Some(v-1)}).is_ok()` (try_down) | `if self.value > 0 { self.value -= 1; true } else { false }` | ✓ Same decision + decrement |
| `fetch_add(1, SeqCst)` | `self.value = self.value + 1` | ✓ Same increment (overflow guard added as precondition) |

## Trust Assumptions (from module documentation)

- **T1**: No arithmetic overflow — `up()` precondition `value < usize::MAX` makes explicit what `fetch_add` silently wraps.
- **T2**: Condvar correctness — sleep/wake protocol modeled at spec level only.
- **T3**: Sequential ordering — model assumes sequential execution; original uses `SeqCst`.
- **T4**: Caller safety conditions — encoded as `Ghost<CallerContext>` preconditions.
- **T5**: `notify_first()` success — original returns `Result`, model assumes success.
- **T6**: `Condvar::wait()` success — original returns `Result<(), SleepError>`, model preconditions guarantee success path.

## Review Response

The following issues were raised in the review (`exec-integrity_20260214_064857.md`)
and addressed in this updated report:

1. **[High] `unsafe` keyword removal not catalogued.** Added as difference #5
   (TYPE_CHANGE). The safety obligations are encoded via `Ghost<CallerContext>`
   preconditions, which is documented in T4 and the `CallerContext` spec.

2. **[Medium] Difference 1 conflated type and visibility changes.** Split into
   difference #1 (type: `AtomicUsize` → `usize`) and difference #2 (visibility:
   private → `pub`). The visibility deviation from Nanvix coding standards is now
   explicitly noted with its justification (Verus tooling constraint).

3. **[Medium] `DownOutcome` enum not listed.** Added as difference #19
   (INVENTED_TYPE). It is a new exec-visible type with no original counterpart,
   required to express both outcomes of the non-looping `down_or_block()` model.

4. **[Low] Import changes not listed.** Added as difference #20 (IMPORT_CHANGE).
   These are consequential changes driven by the sequential model and Verus tooling.

## Conclusion

All 20 differences are documented and justified. The verified exec code preserves the
core semaphore arithmetic (decrement-if-positive for down/try_down, increment for up)
while replacing concurrent primitives (`AtomicUsize`, `Condvar`) with a sequential model
amenable to Verus verification. The two invented functions are side-effect-free accessors
used only for proof connectivity. The one invented type (`DownOutcome`) is required for
the non-looping model of `down()`. No fixes required.
