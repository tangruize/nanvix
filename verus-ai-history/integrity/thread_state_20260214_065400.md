## Trust Assumptions

| ID | Assumption | Justification |
|----|-----------|---------------|
| T1 | No double-locking: `store_mutex_guard` requires `!spec_has_mutex(address)` | In the original kernel, double-locking the same mutex causes a deadlock, so this condition always holds in correct executions. The precondition formalizes this kernel invariant |
| T2 | Release-what-you-hold: `take_mutex_guard` requires `spec_has_mutex(address)` | In the original kernel, a thread releases only mutexes it holds. The original returns `Option<MutexGuard>`, handling the not-found case with `None`. The verified model eliminates that path by construction. The return type change (`Option<MutexGuard>` → `()`) follows from this: if the mutex is always held, the `None` case is unreachable, and the `MutexGuard` payload is opaque |

## Conclusion

All differences between the original and verified exec code are attributable to:
1. **Type abstraction** (7 items): Complex kernel types (`KernelStack`, `UserStack`, `ContextInformation`, `FpuState`, `Condvar`, `MutexGuard`, `BTreeMap`, `Pin<Box<_>>`) abstracted to `int`/`Option<int>`/`Vec<u64>`/`usize` for verification. Documented in module-level comments.
2. **Ghost annotations** (9 items): `requires`/`ensures` clauses and proof blocks added for verification. No impact on exec semantics.
3. **Documented omissions** (3 items): Functions returning opaque HAL/sync types or raw pointers (`context_mut`, `fpu_state_mut`, `join_cond`) are outside the verification model scope.
4. **Justified invention** (1 item): `check_drop_safe()` models the `Drop::drop()` runtime check and is proven equivalent to `spec_drop_safe()`.

No LOGIC_CHANGE differences were found. All exec-level control flow, arithmetic, and data structure operations in the verified code faithfully model the original source within the documented abstraction boundaries.
